◇ still open

Presenting concurrency

02 / 08
IDEA 1

Live Share pairs people, Git separates their time

These solve two different moments, and it helps to name which is which:

  • VS Code Live Share is for same time, same file — two people editing one section together, like a shared cursor. No merge needed because nothing diverged.
  • Git is for different time or different file — the normal case. Each contributor works on their own branch (feature/section-pricing), commits independently, and opens a Pull Request to bring it into main.
  • A reviewer merges the PR once it looks right — that review step is what catches an off-brand section before it reaches main, not a lock or a live conflict.
  • If two branches genuinely touch the same file, Git shows a merge conflict to resolve by hand. Idea 2 is what keeps that rare.
03 / 08
IDEA 2

One assembler, many owned sections

main.html stays thin — it holds the shell, theme, and slide transitions, then pulls in one file per section: sections/01-problem.html, 02-solution.html, and so on.

  • Each section file has one owner. Two people almost never edit the same file, so the merge conflicts Idea 1 warns about become rare instead of routine.
  • The assembler owner's job narrows to wiring sections together and reading the whole deck for cohesion before a release — not writing every slide.
  • No framework needed: a short build script concatenates the section files into the final index.html at deploy time.
04 / 08
IDEA 3

A written brand rulebook, enforced by a Claude Skill

This repo already has the raw material for it — theme_extract.txt and extract_colors.py pulled the palette and type notes out of the EdgeRed Master Template. The next step is turning that into something reusable:

1. Write it down once

edgered-style.md: hex palette, type scale, spacing rhythm, and the slide layout patterns that repeat across the template — as rules, not just swatches.

2. Package it as a Skill

Anyone generating a new section asks the Skill to build it — it applies the rulebook automatically instead of relying on someone eyeballing the last deck.

The payoff: a section built by a new hire in month one looks exactly as on-brand as one built by whoever owns the template — because the rules live in the Skill, not in one person's memory.

05 / 08
IDEA 4

Host on Azure Static Web Apps

A static HTML deck doesn't need a server — Static Web Apps fits it directly, and it plugs straight into the Git workflow from Idea 1:

  • CI/CD from the repo — a push to main deploys automatically, no separate release step.
  • Free SSL + custom domain — a client-facing URL that isn't a raw *.azurestaticapps.net address.
  • A preview URL per Pull Request — this is the quiet concurrency win: a reviewer can open a contributor's branch as a live link and see the real section render before approving the merge, instead of reading a diff.
  • No server cost for a deck with no backend — matches the low-risk, static-first direction already in executive-summary.md.

07 / 08
Added — closing the gap

The remote-control problem still needs an answer

None of the four ideas touch what happens when two people try to drive the same live deck at once in front of a client — the exact scenario flagged in the original call questions. It doesn't need solving today, but it's worth having a plan for:

Default — no build needed

Single-presenter, shared link

Everyone opens the same URL, but only the presenter's keyboard moves the slide. Covers the vast majority of client meetings with zero new infrastructure.

Only if actually needed

One shared nav-state, one driver

A tiny realtime store (Firebase Realtime DB, Supabase Realtime, or a plain WebSocket) holds the current slide index. Whoever holds "driver" publishes changes; everyone else's browser just listens and jumps — with a "request control" button so two clicks can't race each other.

Keep it as an opt-in layer on top of the static deck, not baked into the base build — most presentations should stay as simple as Idea 4 already makes them.
